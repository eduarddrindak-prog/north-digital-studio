1. Что такое Studio Brain
Назначение

Studio Brain — это локальная система исполнения команд, позволяющая языковой модели безопасно взаимодействовать с проектом пользователя.

Вместо предположений о содержимом проекта или генерации изменений "вслепую", модель получает возможность выполнять реальные операции над проектом через набор строго определённых команд.

Studio Brain не заменяет языковую модель.

Он расширяет её возможности.

Языковая модель отвечает за анализ, планирование и принятие решений.

Studio Brain отвечает за выполнение этих решений.

Таким образом система разделяет обязанности:

GPT думает.
Studio Brain выполняет.
Основной принцип

Studio Brain никогда самостоятельно не принимает решений.

Он не анализирует код.

Не планирует изменения.

Не исправляет ошибки.

Он лишь выполняет команды, которые сформировала языковая модель.

Поэтому именно качество решений GPT определяет качество итоговой работы.

Что умеет Studio Brain

Studio Brain предоставляет безопасный доступ к возможностям проекта.

В частности он позволяет:

читать файлы;
создавать и изменять файлы;
искать файлы и текст;
выполнять поиск по регулярным выражениям;
редактировать существующий код;
работать с директориями;
запускать команды терминала;
запускать npm scripts;
получать информацию о файлах;
выполнять операции перемещения и копирования;
откатывать поддерживаемые изменения.
Что Studio Brain не делает

Studio Brain не является IDE.

Studio Brain не является AI.

Studio Brain не анализирует архитектуру проекта.

Studio Brain не принимает решений.

Studio Brain не исправляет ошибки автоматически.

Studio Brain не генерирует код самостоятельно.

Все интеллектуальные решения принимает исключительно языковая модель.

2. Модель мышления при работе со Studio Brain

Этот раздел является наиболее важным.

При работе со Studio Brain модель должна изменить привычный способ взаимодействия с проектом.

Не предполагай — проверяй

Никогда не делай выводов о содержимом проекта без получения данных.

Если необходимо узнать структуру проекта — сначала запроси её.

Если необходимо узнать содержимое файла — сначала прочитай файл.

Если необходимо узнать наличие функции — сначала выполни поиск.

Любые изменения должны основываться на фактическом состоянии проекта.

Сначала информация — потом изменения

Правильный порядок действий практически всегда выглядит следующим образом:

Получить информацию.
Проанализировать результат.
Спланировать изменение.
Выполнить изменение.
Проверить результат.

Не следует выполнять запись до тех пор, пока не получена вся необходимая информация.

Каждая команда должна иметь цель

Не используй команды "на всякий случай".

Перед формированием каждой команды необходимо понимать:

зачем она выполняется;
какую информацию должна вернуть;
каким будет следующий шаг после получения результата.
Минимизируй изменения

Всегда стремись изменить только то, что действительно необходимо.

Не переписывай файл полностью, если можно изменить небольшой фрагмент.

Не создавай новые файлы без необходимости.

Не запускай тяжёлые операции, если достаточно локального изменения.

Работай итеративно

Большие задачи следует разбивать на небольшие этапы.

После каждого этапа необходимо анализировать результат и только затем переходить к следующему.

Studio Brain значительно эффективнее работает через последовательность небольших операций, чем через одну огромную команду.

3. Общий цикл работы

Практически любая задача должна проходить через один и тот же процесс.

Шаг 1

Проанализировать запрос пользователя.

Определить конечную цель.

Шаг 2

Определить, какой информации не хватает.

Если информации недостаточно — сначала получить её.

Шаг 3

Выбрать минимальный набор команд, необходимых для решения задачи.

Не использовать лишние операции.

Шаг 4

Сформировать один или несколько SB-блоков.

Каждый блок должен выполнять одну конкретную задачу.

Шаг 5

Получить результат выполнения.

Никогда не игнорировать ошибки.

Всегда анализировать полученный ответ.

Шаг 6

Если задача ещё не завершена — построить следующий этап, используя уже полученные результаты.

Основной принцип

Studio Brain предназначен для последовательного взаимодействия.

Практически никогда не следует пытаться выполнить всю задачу одним большим запросом.

Лучший результат достигается через цикл:

анализ → получение данных → изменение → проверка → следующий этап.

4. Основные принципы эффективной работы

Ниже приведены правила, которым необходимо следовать практически во всех случаях.

1. Сначала поиск

Если неизвестно расположение объекта — сначала используй поиск.

Не открывай случайные файлы.

2. Сначала чтение

Перед изменением файла желательно ознакомиться с его текущим содержимым.

Изменения не должны строиться на предположениях.

3. Минимизируй объём чтения

Не следует читать весь проект.

Получай только ту информацию, которая необходима для текущей задачи.

4. Минимизируй объём записи

Если изменение можно выполнить локально — не переписывай весь файл.

Предпочитай точечные операции.

5. Избегай лишних shell-команд

Команды терминала должны использоваться только тогда, когда задачу невозможно решить встроенными средствами Studio Brain.

6. Проверяй результат

После важных изменений желательно убедиться, что они действительно были выполнены корректно.

7. Работай последовательно

Каждый следующий шаг должен строиться на результатах предыдущего.

Не принимай решения заранее.

8. Используй возможности Studio Brain

Если задача может быть решена специализированной командой Studio Brain, предпочтительно использовать её вместо универсального подхода.

9. Не дублируй действия

Не выполняй повторный поиск или повторное чтение, если необходимая информация уже была получена и остаётся актуальной.

10. Всегда стремись к минимальному количеству операций

Наилучшее решение — то, которое достигает цели с минимальным количеством команд при сохранении понятности и надёжности.

5. Язык Studio Brain (DSL)
Общая концепция

Все действия в Studio Brain выполняются через специальные блоки команд.

Каждый блок описывает одну логическую операцию, которую должна выполнить система.

После получения ответа ChatGPT не взаимодействует с файловой системой напрямую. Вместо этого он формирует один или несколько SB-блоков, содержащих необходимые инструкции.

Структура блока

Каждая команда записывается внутри блока:

[[SB]]

...

[[/SB]]

Каждый блок представляет собой одну команду.

Если необходимо выполнить несколько различных действий, используется несколько отдельных SB-блоков.

Не следует объединять разные действия в один блок.

Общий синтаксис

Каждая строка представляет собой пару:

КЛЮЧ: значение

Например:

ACTION: READ_FILE
PATH: src/index.ts

Названия ключей не чувствительны к регистру.

Пустые строки игнорируются.

Многострочные значения

Если значение содержит несколько строк, используется строковый литерал.

Внутри него допускаются переносы строк и управляющие символы.

Поддерживаются стандартные escape-последовательности:

\n
\t
\r
\\
\"
\'
\uXXXX
\xXX
Дополнительные параметры

Некоторые команды могут содержать дополнительные поля.

Например:

DRY_RUN
BLOCK_ID
параметры конкретной команды.

Неиспользуемые параметры не следует добавлять.

Один блок — одна задача

Каждый SB-блок должен иметь одну понятную цель.

Правильно:

прочитать файл;
найти текст;
заменить текст.

Неправильно:

прочитать файл;
изменить файл;
выполнить build.

Такие действия следует разделять на несколько последовательных блоков.

8. Архитектура Studio Brain

Понимание внутренней архитектуры не требуется для повседневной работы, однако позволяет лучше понимать ограничения системы.

Общая схема
ChatGPT
    │
    ▼
Chrome Extension
    │
    ▼
Transport Layer
    │
    ▼
BrowserBridge
    │
    ▼
SBParser
    │
    ▼
CommandExecutor
    │
    ▼
ProjectEngine
    │
    ├──────────────► File System
    │
    └──────────────► Terminal
Назначение компонентов
Chrome Extension

Получает ответы ChatGPT.

Извлекает SB-блоки.

Передаёт их локальному серверу.

Получает результаты выполнения.

Transport

Передаёт сообщения между расширением и локальным процессом Studio Brain.

Не содержит логики выполнения.

BrowserBridge

Получает текст.

Находит SB-блоки.

Передаёт их парсеру.

SBParser

Преобразует текстовые команды DSL во внутренние объекты команд.

Не выполняет никаких операций.

CommandExecutor

Проверяет корректность команды.

Создаёт транзакции.

Передаёт выполнение ProjectEngine.

Формирует результат выполнения.

ProjectEngine

Выполняет всю реальную работу.

Именно этот компонент взаимодействует с:

файловой системой;
директориями;
поиском;
терминалом;
npm.

Все изменения проходят через него.

ExecutionHistory

Хранит историю выполненных транзакций.

Используется для поддержки отката изменений и хранения информации о предыдущих действиях.

Принцип разделения ответственности

Каждый компонент системы отвечает только за одну область.

Extension взаимодействует с ChatGPT.
Transport передаёт сообщения.
Parser понимает язык команд.
Executor управляет выполнением.
Engine работает с проектом.

Благодаря такому разделению архитектура остаётся модульной, а изменение одного компонента практически не влияет на остальные.



Работа с файлами
READ_FILE
Назначение

Команда READ_FILE используется для чтения полного содержимого существующего файла.

Команда не изменяет проект и применяется для анализа исходного кода, конфигураций, документации или любых других файлов перед дальнейшими действиями.

Когда использовать

Используй READ_FILE, если необходимо:

понять существующую реализацию;
изучить содержимое файла;
подготовиться к редактированию;
проверить результат после изменения;
проанализировать код перед поиском ошибки.
Когда НЕ использовать

Не используй READ_FILE, если:

неизвестно расположение файла — сначала используй FIND_FILES;
необходимо прочитать только несколько строк — используй READ_LINES;
требуется только проверить существование файла — используй EXISTS.
Как думает GPT

Пользователь попросил изменить компонент LoginPage.

Прежде чем изменять код, необходимо понять его текущую реализацию.

Следовательно сначала нужно прочитать файл.

Типичный запрос пользователя

Добавь кнопку "Forgot password" на страницу входа.

SB-блок
[[SB]]
ACTION: READ_FILE
PATH: src/pages/LoginPage.tsx
[[/SB]]
Что вернёт Studio Brain

Полное содержимое файла src/pages/LoginPage.tsx.

Что GPT должен сделать дальше

После получения содержимого:

Проанализировать код.
Определить место внесения изменений.
Использовать подходящую команду редактирования (INSERT_TEXT, REPLACE_TEXT и т.д.).
READ_LINES
Назначение

Команда READ_LINES читает только определённый диапазон строк файла.

Используется для уменьшения объёма читаемых данных, когда полный файл не требуется.

Когда использовать

Используй READ_LINES, если:

уже известно расположение нужного участка;
необходимо проверить небольшой фрагмент;
требуется перечитать изменённую область;
файл очень большой.
Когда НЕ использовать

Не используй READ_LINES, если:

неизвестно расположение нужного кода;
необходимо понять архитектуру всего файла;
читается файл впервые.
Как думает GPT

Я уже знаю, что нужная функция находится примерно около 250 строки.

Нет смысла читать весь файл повторно.

Типичный запрос пользователя

Покажи реализацию метода handleSubmit.

После предыдущего поиска известно, что функция находится около строки 180.

SB-блок
[[SB]]
ACTION: READ_LINES
PATH: src/components/Form.tsx
START_LINE: 170
END_LINE: 230
[[/SB]]
Что вернёт Studio Brain

Только строки с 170 по 230.

Что GPT должен сделать дальше

Проанализировать полученный участок и принять решение о дальнейшем редактировании.

WRITE_FILE
Назначение

Команда WRITE_FILE полностью записывает новое содержимое файла.

Если файл существует, его содержимое будет полностью заменено.

Когда использовать

Используй WRITE_FILE, если:

создаётся полностью новая версия файла;
файл генерируется целиком;
локальное редактирование невозможно или нецелесообразно.
Когда НЕ использовать

Не используй WRITE_FILE, если требуется:

заменить несколько строк;
добавить небольшой участок кода;
удалить один блок.

В таких случаях предпочтительнее использовать специализированные команды редактирования.

Как думает GPT

Пользователь попросил полностью переписать конфигурационный файл.

Частичная замена только усложнит выполнение.

Следовательно проще записать новое содержимое целиком.

Типичный запрос пользователя

Полностью обнови файл docker-compose.yml согласно новой конфигурации.

SB-блок
[[SB]]
ACTION: WRITE_FILE
PATH: docker-compose.yml
CONTENT: |
  version: "3.9"

  services:
    app:
      build: .
      ports:
        - "3000:3000"
[[/SB]]
Что вернёт Studio Brain

Подтверждение успешной записи файла.

Что GPT должен сделать дальше

При необходимости:

выполнить READ_FILE для проверки;
запустить BUILD или RUN_COMMAND, если изменение влияет на сборку.
CREATE_FILE
Назначение

Создаёт новый файл.

Если файл уже существует, команда завершится ошибкой.

Когда использовать

Используй CREATE_FILE, если:

пользователь просит создать новый файл;
необходимо добавить новый компонент;
создаётся новый конфигурационный файл;
создаётся документация.
Когда НЕ использовать

Не используй CREATE_FILE, если:

файл уже существует;
требуется изменить существующий файл — используй WRITE_FILE или команды редактирования.
Как думает GPT

Пользователь попросил создать новый React-компонент.

Такого файла ещё нет.

Следовательно необходимо создать новый файл.

Типичный запрос пользователя

Создай новый компонент UserCard.

SB-блок
[[SB]]
ACTION: CREATE_FILE
PATH: src/components/UserCard.tsx
CONTENT: |
  export default function UserCard() {
      return <div>UserCard</div>;
  }
[[/SB]]
Что вернёт Studio Brain

Главное правило

Никогда не открывай файлы наугад.

Если расположение файла неизвестно — сначала используй FIND_FILES.

Если неизвестно, где используется объект — сначала используй SEARCH_TEXT.

Если требуется найти множество похожих конструкций — используй SEARCH_REGEX.

Только после получения результатов поиска переходи к чтению (READ_FILE или READ_LINES) и последующему редактированию. Это минимизирует количество операций и соответствует принципу Studio Brain: сначала найти нужную информацию, затем работать только с ней.

# 5. Studio Brain DSL

## Что такое DSL

Studio Brain использует собственный Domain Specific Language (DSL), через который ChatGPT передаёт инструкции на выполнение.

Каждая инструкция представляет собой один или несколько SB-блоков.

Общая схема выглядит следующим образом:

```text
ChatGPT
    ↓
SB DSL
    ↓
BrowserBridge
    ↓
SBParser
    ↓
CommandExecutor
    ↓
ProjectEngine
```

GPT не взаимодействует с файловой системой напрямую.

Он описывает намерение в виде SB-блока, после чего Studio Brain самостоятельно выполняет необходимое действие.

---

## Общий формат блока

Каждая команда оформляется следующим образом:

```text
[[SB]]
ACTION: COMMAND_NAME
...
[[/SB]]
```

Например:

```text
[[SB]]
ACTION: READ_FILE
PATH: src/App.tsx
[[/SB]]
```

---

## Структура команды

Каждая команда состоит из набора параметров.

```text
ACTION: READ_FILE
PATH: src/App.tsx
```

где

* ACTION — тип команды
* остальные поля — параметры команды

Названия параметров зависят от конкретной операции.

---

## Многострочные значения

Если параметр содержит несколько строк, используется синтаксис:

```text
CONTENT: |
  первая строка
  вторая строка
  третья строка
```

Studio Brain сохранит переносы строк без изменений.

---

## Несколько команд

Несколько независимых действий оформляются отдельными SB-блоками.

Если действия являются одной логической операцией, используется команда `RUN`.

---

## Основные принципы DSL

При работе с DSL GPT должен соблюдать следующие правила:

* каждая команда должна иметь понятную цель;
* использовать минимальное количество команд;
* сначала получать информацию, затем изменять проект;
* не выполнять лишние операции;
* использовать специализированные команды вместо Shell;
* объединять команды только тогда, когда это действительно необходимо.

---

## BrowserBridge

BrowserBridge получает сообщения от расширения браузера, извлекает SB-блоки и передаёт их на выполнение.

Основные задачи:

* поиск SB-блоков;
* разбор ответа ChatGPT;
* запуск выполнения;
* возврат результатов.

---

## SBParser

SBParser преобразует DSL в объекты команд.

Он отвечает за:

* синтаксический анализ;
* проверку структуры;
* разбор параметров;
* обработку многострочных значений.

---

## CommandExecutor

CommandExecutor является координатором выполнения.

Он:

* валидирует команды;
* создаёт транзакции;
* передаёт выполнение ProjectEngine;
* сохраняет историю;
* обеспечивает возможность отката.

---

## ProjectEngine

ProjectEngine выполняет реальные действия над проектом.

Он отвечает за:

* работу с файлами;
* работу с директориями;
* поиск;
* редактирование;
* выполнение shell-команд;
* безопасность файловой системы;
* обработку транзакций.

Именно ProjectEngine взаимодействует с файловой системой и терминалом.

---

## Почему GPT должен понимать архитектуру

Понимание архитектуры помогает модели принимать более правильные решения.

Например:

* `READ_FILE` не читает файл самостоятельно — он создаёт запрос к ProjectEngine.
* `SEARCH_TEXT` не анализирует проект внутри модели — поиск выполняет движок.
* `RUN_COMMAND` не исполняется ChatGPT — команда передаётся в терминал через ProjectEngine.
* `UNDO_LAST_TRANSACTION` работает благодаря системе транзакций CommandExecutor.

Поэтому GPT должен рассматривать Studio Brain как **исполнитель**, а себя — как **планировщика**. Его задача заключается не в непосредственном изменении проекта, а в формировании корректной последовательности действий, которую затем выполнит Studio Brain. Это разделение ответственности лежит в основе всей архитектуры системы и является ключевым принципом эффективной работы с ней.

Обработка ошибок

Studio Brain использует двухуровневую обработку ошибок:

1. Ошибки валидации

Возникают до выполнения команды:

отсутствует обязательный параметр;
неверный MODE;
неверный диапазон строк;
некорректное регулярное выражение;
путь не существует (для операций чтения и поиска).

В этом случае команда не запускается.

2. Ошибки выполнения

Возникают внутри ProjectEngine:

отказ файловой системы;
ошибка shell-команды;
нарушение sandbox;
невозможность записи;
исключения Node.js.

Все такие ошибки преобразуются в стандартный SBExecutionResult с success: false, поэтому GPT получает единый формат ответа независимо от причины сбоя.

Назначение

Данная глава описывает формат ответов Studio Brain после выполнения команд DSL.

Каждая успешно распознанная команда возвращает объект типа SBExecutionResult, содержащий информацию о результате выполнения, времени выполнения, диагностике и дополнительных данных.

Общая модель ответа

Каждая команда возвращает один объект результата.

Интерфейс результата:

interface SBExecutionResult {
    success: boolean;
    action: string;
    path?: string;
    message: string;
    durationMs: number;

    stdout?: string;
    stderr?: string;
    exitCode?: number;
    command?: string;

    blockId?: string;
    dryRun?: boolean;

    data?: Record<string, unknown>;

    warnings?: string[];
    errors?: string[];
}

Обязательные поля

Каждый результат содержит следующие поля.

Поле	Тип	Описание
success	boolean	Успешно ли выполнена команда
action	string	Имя выполненной команды
message	string	Краткое описание результата
durationMs	number	Время выполнения в миллисекундах
Необязательные поля

Следующие поля присутствуют только при необходимости.

Поле	Когда появляется
path	Команда работает с одним файлом
stdout	Shell-команда что-либо вывела
stderr	Shell вернул ошибку
exitCode	Выполнялась shell-команда
command	Использовался RUN_COMMAND
blockId	Команда выполнялась внутри SB-блока
dryRun	Команда запускалась в режиме DRY_RUN
data	Дополнительные структурированные данные
warnings	Есть предупреждения

19. Bridge Protocol
Назначение

Bridge Protocol описывает механизм взаимодействия между ChatGPT, Chrome Extension и Studio Brain.

Bridge отвечает исключительно за транспорт сообщений.

Он не анализирует, не изменяет и не интерпретирует содержимое сообщений.

Вся логика обработки находится внутри Studio Brain.

Общая архитектура

Взаимодействие компонентов происходит следующим образом.

ChatGPT

↓

Content Observer

↓

StudioBrainBridge

↓

HTTP POST

↓

Studio Brain

↓

Server-Sent Events (SSE)

↓

StudioBrainBridge

↓

ChatGPT Input

↓

Send

Bridge работает одновременно в двух направлениях:

передача сообщений из ChatGPT в Studio Brain;
получение ответов Studio Brain и отправка их обратно в ChatGPT.
Основные компоненты

Bridge состоит из двух независимых частей.

Forward Transport

Передача сообщений ChatGPT → Studio Brain.

Использует HTTP POST.

Reverse Transport

Передача сообщений Studio Brain → ChatGPT.

Использует Server-Sent Events (SSE).

Жизненный цикл сообщения

Полный цикл обработки сообщения выглядит следующим образом.

ChatGPT завершил генерацию

↓

Observer обнаружил новое сообщение

↓

Ожидание стабилизации текста

↓

Извлечение текста

↓

HTTP POST

↓

Studio Brain

↓

Обработка команды

↓

SSE

↓

Очередь сообщений

↓

Вставка в поле ввода

↓

Нажатие Send
Завершение генерации

Bridge не отправляет сообщение сразу после появления текста.

Перед отправкой выполняются дополнительные проверки.

Сообщение считается завершённым только если одновременно выполнены следующие условия:

сообщение содержит текст;
длина текста превышает 20 символов;
текст перестал изменяться;
текст остаётся неизменным в течение пяти последовательных проверок;
проверка выполняется один раз в секунду.

Это предотвращает отправку неполных ответов ChatGPT.

Проверка стабильности

Алгоритм можно представить следующим образом.

Получить текст

↓

Изменился?

↓

Да

↓

Сбросить таймер

↓

Нет

↓

Stable Count++

↓

Stable Count == 5

↓

Сообщение завершено
Защита от повторной отправки

Каждое сообщение ChatGPT имеет собственный постоянный идентификатор.

Используется:

data-turn-id

После успешной отправки идентификатор помещается во внутренний список обработанных сообщений.

Поэтому одно сообщение может быть отправлено Studio Brain только один раз.

Даже если DOM страницы позже изменится.

История сообщений

При запуске расширения вся существующая история диалога помечается как уже обработанная.

Это предотвращает повторную отправку старых сообщений при обновлении страницы.

Новые сообщения начинают отслеживаться только после запуска Observer.

Content Observer

Bridge использует MutationObserver.

Отслеживаются:

новые сообщения ChatGPT;
изменение DOM;
появление новых assistant-секций.

Observer не реагирует на пользовательские сообщения.

Извлечение текста

Перед отправкой Bridge получает только отображаемый текст сообщения.

Используется внутренний DOM-парсер:

extractVisibleText()

Это означает:

HTML не передаётся;
Markdown не передаётся;
служебные элементы ChatGPT игнорируются.

Studio Brain получает только итоговый текст ответа.

Формат исходящего сообщения

Каждое сообщение передаётся HTTP POST запросом.

Адрес:

http://localhost:3847/message

Формат сообщения соответствует интерфейсу BridgeMessage.

{
    "type": "CHATGPT_MESSAGE",
    "source": "extension",

Независимость транспорта

Bridge не знает:

Bridge является полностью транспортным уровнем.

Bridge гарантирует:

сохранение порядка сообщений;
передачу только завершённых ответов;
автоматическую очередь отправки;
автоматическое ожидание завершения генерации ChatGPT;
разделение транспортного уровня и логики Studio Brain.

Bridge не гарантирует:

выполнение команд Studio Brain;
успешное HTTP-соединение;
доступность сервера;
корректность содержимого payload;
автоматическое восстановление логических ошибок Studio Brain.

Bridge отвечает исключительно за передачу сообщений между компонентами системы.

Принципы архитектуры

Studio Brain построен на следующих принципах:

Single Responsibility — каждый компонент выполняет одну задачу.
Layered Architecture — логика разделена на независимые уровни.
Deterministic Execution — одинаковый ввод приводит к одинаковому результату.
Safety First — все операции проходят проверку перед выполнением.
Transaction Awareness — изменения проекта могут быть отслежены и, где возможно, отменены.
Transport Isolation — транспортный уровень полностью отделён от логики выполнения.
